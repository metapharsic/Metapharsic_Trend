# Trend MR — spec conformance findings

Produced by `qa/tools/diff-spec.mjs` and the contract invariants, then verified
by reading each cited file. Every finding below was confirmed in source; none
are inferred.

Scope of this pass: 110 API routes, 49 screens, 3 authored screen specs
(`orders`, `collections`, `mr-claims`). Screens without a spec are covered only
by the repo-wide invariants.

---

## HIGH

### 1. `/api/invoices` disagrees with its siblings about who is a manager

- **Where:** `web/app/api/invoices/route.ts:8`
- **Observed:** `isManager = role === ASM || role === ADMIN`.
  `/api/orders/secondary` and `/api/orders/history` both use
  `ASM || ADMIN || MD`. The route's own `withAuth` list is
  `[MR, ASM, ADMIN]` — MD is not admitted at all.
- **Consequence:** On `/orders`, an MD sees every order and the full ledger
  history, but the Generated Invoices tab either 403s or falls through the
  `!isManager` branch to `employee.findUnique({ userId })`, which for an MD with
  no Employee row returns `401 Employee record not found`. Three tabs on one
  screen, two scope rules.
- **This is the exact bug class `CLAUDE.md` documents**, in a route that was
  not part of the earlier fix.
- **Fix:** hoist the manager-role list into one shared helper and have all three
  routes call it. The contract test
  `sibling endpoints agree on which roles bypass personal scope` locks it.

### 2. Seven endpoints silently truncate their result set

- **Where:**

  | Route | Cap |
  |---|---|
  | `app/api/invoices/route.ts` | `take: 500` |
  | `app/api/orders/history/route.ts` | `take: 500` ×3 |
  | `app/api/distributor/invoices/route.ts` | `take: 500` |
  | `app/api/manager/visits/map/route.ts` | `take: 1000` |
  | `app/api/manager/notifications/route.ts` | `take: 200` |
  | `app/api/manager/mr-stock/history/route.ts` | `take: 200` |
  | `app/api/products/[id]/movements/route.ts` | `take: 100` |

- **Observed:** each caps rows with no `skip`/`page` and returns no total.
- **Consequence:** row 501 does not exist as far as any caller is concerned, and
  no client can detect the truncation. For an established distributor this is
  reached in normal use, not at the edge.
- **Fix:** paginate properly, or return `pagination.total` alongside the capped
  page so the UI can say "showing 500 of 1,240".

### 3. Header counts are rendered from array length

- **Where:** `web/app/(dashboard)/orders/page.tsx:293,307` and
  `web/app/(dashboard)/admin/claims/page.tsx`
- **Observed:** `Generated Invoices ({invoices.length})`,
  `Complete History ({history.length})`, `Pending ASM Review ({pending.length})`.
- **Consequence:** combined with finding 2, these headers read `500` forever once
  the cap is hit — a wrong number displayed with total confidence. This is the
  visible half of the original orders-vs-invoices report and is **still live**;
  only the scoping half was fixed.
- **Fix:** render `pagination.total`. Guarded by the contract test
  `no screen renders a heading count from a paginated array's length`.

## MEDIUM

### 4. `/api/mr/ledgers` returns a different pagination shape from its sibling

- **Where:** `web/app/api/mr/ledgers/route.ts:36`
- **Observed:** returns `{ ledgers, total, page, limit }`.
  `/api/manager/ledgers` returns `{ ledgers, pagination: { page, limit, total, totalPages } }`.
- **Consequence:** any shared client helper reading `data.pagination.total` gets
  `undefined` on the MR route and renders a blank or `NaN` count. It is the
  cheapest possible bug to fix and the hardest to notice.

### 5. Order-entry fields cannot be addressed by any automation

- **Where:** `web/app/(dashboard)/orders/page.tsx`
- **Observed:** the quantity, free-qty, discount, batch, expiry, LR-number and
  due-date inputs carry no `name`, `id`, or `data-testid`. They are positional
  only.
- **Consequence:** no Playwright test can fill the order form without brittle
  nth-child selectors, and the QA agent cannot describe which field it is
  reporting on. This is one convention gap, not seven bugs — but it blocks
  browser coverage of the single most important form in the app.
- **Fix:** add `data-testid` to each. `testability.requireSelectors` in
  `orders.yaml` already declares the requirement.

### 6. `/api/users` and `/api/users/[id]` gate on `ALL_ROLES`

- **Where:** `web/app/api/users/[id]/route.ts:186-187`
- **Observed:** `GET` and `PUT` admit the `ALL_ROLES` constant. `DELETE`
  correctly narrows to `[Role.ADMIN]`.
- **Consequence:** worth an explicit decision rather than a shrug — `PUT` on a
  user record open to every role including `DISTRIBUTOR` and `DOCTOR` deserves
  to be deliberate. Recorded in an inline snapshot so adding another is a
  conscious act.

## Not defects

- `/api/logs/frontend` bypasses the response envelope. Exempted — it is a
  fire-and-forget log sink, not a data API.
- `/api/orders/secondary` is clean: consistent scope, `pagination.total`, and
  `groupBy` tallies. It is the reference implementation the others should match.

---

## Suggested order of work

1. Finding 1 — one shared manager-role helper. Smallest change, worst symptom.
2. Finding 3 + 2 together — return totals, then render them. Doing 3 without 2
   just moves the wrong number.
3. Finding 4 — align the ledger response shape.
4. Finding 5 — add `data-testid` to the order form; unblocks browser coverage.
5. Finding 6 — decide, then encode the decision.
